# PetPattern differentiation, activation & trust pass — implementation audit

_Audit before code (spec Part 0). Produced by fanning out one reader per subsystem, then cross-checking the highest-risk findings (pattern engine, `detectionCount`, confidence, food/baseline model) against a first-hand read of the source. **No product code has been changed yet.**_

## Verdict in one line

The product is already ~70% of the way to the spec's thesis: the copy is on-brand and cautious, the Vet Summary already works from the first log, Recap and WeeklyInsight already exist and never dead-end, the timeline exists, Android hardening is intact, and there is a genuine two-way food-elimination verdict engine (`FoodTrialService`). The gaps are concentrated and fixable **by extending existing systems, not building new ones**. Four things are genuinely wrong or missing and carry the most weight:

1. **`detectionCount` is presented as recurrence** (Part 9) — it is really "how many calendar days the engine re-ran and re-surfaced the same one piece of evidence." After 2 days it says *"Seen a few times."* This is the single most important honesty defect.
2. **No evidence-stage model and no counter-evidence** (Parts 8, 10, 11) — cards show a one-sided "supports" list; limitations are `.muted` footer text; nothing ever *weakens*.
3. **"Current main food" is "most-recently-started anything"** (Part 1) — a treat or supplement logged today silently replaces the displayed main food. No active-period/end-date model for food.
4. **A few causal strings** (Part 7) — notably the headline `"Possible {protein}-related pattern"` (verbatim on the forbidden list) and a vet-summary "food-related pattern" line.

Everything else is smaller: quick-log wording conflates "unchanged" with "quiet day", the weekly recap is itching/dog-flavoured rather than species-neutral counts, the timeline lacks visual hierarchy and baseline spans, there is **no draft protection at all**, and **~26 of the 32 required tests do not exist**.

## What must be preserved (do not touch)

Palette / typography / cards / sidebar / nav / visual identity / cautious tone / Capacitor architecture / Android signing, App Links, backup rules, secure session storage, notification anti-spam, minimal permissions. Do **not** rename backend enum wire values (`POSSIBLE_FOOD_TRIGGER`, AI `LOW/MEDIUM/HIGH`, severity `mild/moderate/strong`) — they are persisted in candidate ids (`petId:ruleId`) and asserted by many tests. Only reword *rendered* strings.

**Mechanism.** `PatternEngine.analyze()` recomputes candidates from the **last 120 days on every request**. `PatternMemoryService.listPatterns()` calls `observation.recordDetection()` which does `detectionCount++` **once per calendar day** the same candidate is still surfaced (`PatternObservation.java:166-177`; Javadoc literally: *"how many distinct days it has recurred… bumping the recurrence count once per calendar day"*).

## Agent-audited subsystems (verbatim findings)

### Mobile/Capacitor/Android + build & validation surface

_PetPattern ships as a Capacitor 8 wrapper around the React/Vite web app (frontend/capacitor.config.json: appId app.petpattern.mobile, webDir dist, androidScheme https). There is a single codebase: `npm run build:mobile` runs a preflight then `vite build --mode mobile` into frontend/dist, and `npx cap sync` copies it into the native android project. Native features are all reached through runtime `Capacitor.Plugins.*` globals so the web bundle never links native code: deep links + Android back button + status bar (src/lib/mobile.js), daily local-notification reminder (src/lib/nativeNotifications.js), and OS secure-store session token (src/lib/secureSession.js). Android release hardening is substantial and already in place: conditional release signing driven by an untracked key.properties (android/app/build.gradle:10-30,60-62), backup/transfer lockdown (AndroidManifest allowBackup=false + data_extraction_rules.xml excluding all domains), App Links behind a build-time host placeholder defaulting to the reserved .invalid TLD with autoVerify off (variables.gradle:22-23, AndroidManifest:59-64), and a deliberately minimal permission set (INTERNET + POST_NOTIFICATIONS only, plus RECEIVE_BOOT_COMPLETED/WAKE_LOCK merged from the notifications plugin). Validation surface: npm scripts (test=vitest run, test:e2e=playwright, build, build:mobile), backend via committed Maven wrapper (./mvnw) in CI or Docker locally, and a 4-job CI (.github/workflows/ci.yml) covering frontend tests+build+audit, backend test, Flyway migration boot, and release hygiene/secret scan. Everything native (AAB, debug APK, cap sync output, Android lint, on-device behavior) cannot be produced or run in this environment — no Android SDK/JDK/emulator — and the docs (docs/mobile.md, docs/android-release.md) mark those items honestly as generated/not-verified._

### Persistent baseline data model (food/treats/supplements/meds)

_Today PetPattern has NO real active-period model for food. `FoodLog` (backend/src/main/java/com/petpattern/domain/FoodLog.java) is a point-in-time event row: it has `dateStarted` (lines 24-28, mirrored into a legacy `date` column) and a `foodKind` enum (MAIN_FOOD/TREAT/SUPPLEMENT/OTHER, FoodKind.java) but NO end date, NO replacement relationship, and NO "active" flag. "Current food" is derived purely by recency, regardless of kind: both `FoodLogController.current` (FoodLogController.java:43) and `PetController.overview` (PetController.java:139) call `foodLogRepository.findFirstByPetOrderByDateStartedDesc(pet)`, which returns the single newest row by start date whatever its kind. The frontend renders that as the "Current food" panel (TodayView.jsx:143-160) and falls back to `foodLogs[0]` (App.jsx:139). Consequently a TREAT or SUPPLEMENT logged with today's date silently replaces the displayed main food — the exact behavior Part 1 forbids. There is no way to answer "what was active on date X" for food; the only period-aware food construct is `FoodTrial` (an elimination EXPERIMENT with start/targetEnd/reintroduced/completed/status — FoodTrial.java, TrialStatus.java), which is a different concept and must not be overloaded as a baseline. Medications, by contrast, DO have a correct active-period model (`Medication.startDate` + nullable `endDate`, `ongoing` derived, a `/stop` endpoint) that food should mirror. ActivityLog is unrelated (WALK/PLAY/etc., date-only events)._
